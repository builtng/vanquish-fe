7. FIX E02: DOCUMENT UPLOAD 10MB LIMIT, UPLOAD TOKENIZATION & SECURITY HARDENING (TC & QC)
--------------------------------------------------------------------------------
PROBLEM:
  1. Trainee Counsellor application form bundled all files in a single multipart POST payload,
     exceeding body limits (Cloudflare/Nginx 413) without individual progress or clear error feedback.
  2. Public TC upload route (POST /api/tc-intake/upload-document) accepted application_id / trainee_application_id,
     allowing unauthorized overwrites of applicant documents by guessing IDs.
  3. Public QC upload route (POST /api/qualified-counsellor/upload-document) accepted qc_application_id, application_id,
     or tc_id, allowing unauthorized overwrites of existing QC application documents.
  4. The final submit steps (tcIntake and submitQualifiedForm) accepted arbitrary strings as document paths,
     permitting outside URLs or raw storage paths.
  5. TraineeApplicationController::downloadDocument and QcApplicationController::downloadDocument could redirect
     admin users to untrusted external URLs.

FIX:
  1. Dedicated single-file upload endpoints for both TC and QC forms:
     - POST /api/tc-intake/upload-document (IntakeFormController)
     - POST /api/qualified-counsellor/upload-document (TrainingCounsellorController)
     Both routes accept one document up to 10MB (10240 KB), enforce mime & extension validation,
     store strictly on the 'private' disk, and return a single-use 40-character upload token cached for 24 hours.
  2. Removed all application_id, qc_application_id, tc_id, and uuid handling from both upload endpoints.
  3. Both upload routes are protected by rate limiting (throttle:60,1).
  4. Final submission handlers (tcIntake & submitQualifiedForm) accept only valid one-time upload tokens for pre-uploaded documents:
     resolves token to stored private path, attaches to application and intake form, then deletes token from cache.
  5. External URLs, raw storage paths, and invalid/expired tokens are strictly rejected with HTTP 422.
  6. In both downloadDocument methods, external redirects are restricted strictly to trusted JotForm domains (*.jotform.com,
     *.jotformeu.com, *.jotformpro.com, files.jotform.com), blocking untrusted redirects with HTTP 403.
  7. Frontend client-side validation immediately rejects files > 10MB before network call.
  8. Individual uploads with live upload progress indicators ("Uploading... 45%") and real error messages (413 / 422).

13. FIX Z03: SERVER-ENFORCED PRICING ON PAYMENT INTENTS (CONSULTATION, SESSION, BLOCK)
--------------------------------------------------------------------------------
PROBLEM:
The browser was passing an `amount` field directly to POST /api/payments/create-intent.
An adversary or manipulated client could tamper with the amount payload and pay 50p
for a consultation, single session, or block of sessions.

FIX:
  1. Updated PaymentController::createPaymentIntent to ignore the browser-supplied amount
     completely and calculate the authoritative price on the server:
     - Consultation: fetched from ServiceSetting for client's service_type (consultation_price).
     - Session: fetched from ServiceSetting (session_price) multiplied by count of session_ids.
     - Block: fetched from ServiceSetting (block_price), falling back to 4x session_price.
  2. Applied valid coupon discounts server-side against the server-computed amount.
  3. Added automated feature tests in backend/tests/Feature/SecurityZ03Z04FixTest.php
     verifying that arbitrary browser amounts (£0.50) are overridden by the live ServiceSetting price.

FILES MODIFIED / CREATED:
  - backend/app/Http/Controllers/Api/PaymentController.php
  - backend/tests/Feature/SecurityZ03Z04FixTest.php

TESTS VERIFIED:

14. FIX Z04: BLIND CLIENT BOOKING AUTHENTICATION & ENUMERATION PREVENTION
--------------------------------------------------------------------------------
PROBLEM:
POST /api/client-booking/authenticate previously accepted an email alone and returned
the full client object (name, service type, allocated day/time, deadlines, matched counsellor).
This allowed unauthenticated attackers to query arbitrary emails to determine if someone is
a Vanquish client and expose their sensitive therapy details.

FIX:
  1. When a client visits the private booking page with their valid uuid (?uuid=...),
     full booking and profile details are returned securely.
  2. If only an email address is provided without a valid client uuid:
     - The endpoint returns NO client data.
     - It returns a generic message: "If this email is registered, we have sent you your booking link."
     - If the email is registered, the backend dispatches an email to the client with their private booking link.
     - If the email is not registered, the identical HTTP 200 generic message is returned, preventing email enumeration.
  3. Added automated feature tests in backend/tests/Feature/SecurityZ03Z04FixTest.php verifying
     identical response messages for registered vs unregistered emails, no client data leakage, and
     successful authentication with valid uuid.

FILES MODIFIED / CREATED:
  - backend/app/Http/Controllers/Api/ClientBookingController.php
  - backend/tests/Feature/SecurityZ03Z04FixTest.php
